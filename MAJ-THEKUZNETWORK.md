4. Compare shared status, repository links, publication state and cross-project dependencies.
5. Create a recoverable Git backup before modifying existing tracked content.
6. Correct only verified inconsistencies or defects.
7. Update README and current documentation in every repository where state changed.
8. Preserve frozen protocols, historical reports, receipts and dated historical snapshots as immutable evidence.
9. Verify that secrets, tokens, credentials and private data are not introduced.
10. Report each repository as UPDATED or NO CHANGE with the reason.

## Mini-Kuzai DEV-FLOW rule

`MAJ-THEKUZNETWORK` never authorizes training, optimizer steps, BLIND access or checkpoint mutation.

When the next Mini-Kuzai scientific step reaches the publication boundary, the operator must be explicitly warned that `START-DEV-FLOW` is required before it is launched.

A `FINAL-DEV-FLOW` closure must be followed by `MAJ-THEKUZNETWORK` before the next scientific step advances.

## FINAL closure verification

For V83 and later, a `FINAL-DEV-FLOW` is operationally complete only after all of the following are verified -->

- the Mini-Kuzai scientific FINAL receipt is committed
- the cross-channel media receipt is committed in `Mini-Kuzai_YOUTUBE`
- YouTube, LinkedIn native video and GitHub media fallback are verified
- the read-only end-to-end closure audit passes
- the automatic GOGIT report `Vxx-FINAL-DEV-FLOW-AUTO-VERIFY-001` exists and reports `FINAL_FLOW=PASS` and `MEDIA_RECEIPT=PASS`

Normal `MAJ-THEKUZNETWORK` execution follows that verified closure. Recovery/audit work may run earlier only to repair the publication system itself.

This closure evidence never authorizes training, BLIND access, optimizer steps or checkpoint mutation.
